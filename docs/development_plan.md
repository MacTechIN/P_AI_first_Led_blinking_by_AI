# 개발 계획 — Vertical Stackable / Microprocess

`docs/project_difinition.md` 분석에 기반한 실행 계획.
현재 상태는 `docs/project_0_camtest.md` 참조.

---

## 0-A. 프로젝트의 목적 (우선순위를 바꾸는 정보)

**Physical AI 기초 기술을 구현하고, 설명하기 쉬운 사례를 만들어 시범을 보이며,
교육용 커리큘럼을 완성한다.**

따라서 최종 산출물은 동작하는 코드가 아니라 **가르칠 수 있는 자료**다. 이것이
계획에 두 가지 영향을 준다.

1. **기록된 실패가 핵심 자산이다.** 잘 되는 경우만 보여주는 교재는 학습자가
   막히는 순간 쓸모가 없다. `docs/tech/` 의 실패 기록과 ADR 의 기각 사유가
   강의안의 원재료다. 앞으로도 실패를 지우지 말고 남긴다.
2. **기능 확장보다 교재화가 먼저다.** 모듈 0~5(VS-0~VS-4)로 이미 완결된 한
   사이클이 성립한다. VS-5·VS-6 으로 넓히기 전에 실습 지침·예상 출력·연습 문제를
   채우는 편이, 기억이 선명할 때 정확하게 쓸 수 있다.

커리큘럼 구성은 `docs/curriculum.md` 참조.

## 0. 정의서 해석

정의서의 요구를 실행 가능한 형태로 옮기면 다음과 같다.

| 정의서 문구 | 기술적 함의 |
|---|---|
| "AI가 사물을 **스스로** 제어" | 제어 규칙이 코드가 아니라 **모델의 판단**에서 나와야 한다 |
| "**프로그램 불필요**" | 새 동작 추가 = 코드 수정이 아니라 **역량 선언 + 프롬프트** 변경 |
| "카메라 이미지 분석 후 LED 제어" | 인지 → 판단 → 구동의 **종단 루프**가 성립해야 한다 |
| "동일 색 표시, 방향 표시 등 **알아서 판단**" | 출력이 고정 명령이 아니라 **상황 해석의 결과** |
| "**독립적인** 환경 구축" | 외부 API 의존 없이 **온디바이스 추론** (오프라인 동작) |
| "기초 이론 확립 및 스터디" | 산출물에 **재현 가능한 기록**이 포함되어야 한다 |
| (추가) 교육용 커리큘럼 완성 | 실패·대안·측정 과정까지 **가르칠 수 있는 형태**로 남긴다 |

핵심 긴장 관계 두 가지를 먼저 인식해야 한다.

1. **LLM은 느리고 제어는 빨라야 한다.** VLM 추론은 초 단위, LED/모터 제어는
   밀리초 단위다. 하나의 루프로 묶으면 둘 다 망가진다.
   → **느린 정책 루프(AI)와 빠른 제어 루프(MCU)를 분리한다.**
   Project 0에서 점멸 타이밍을 아두이노에 둔 것이 이 원칙의 첫 적용이었다.

2. **LLM은 틀린다.** 스키마 위반, 환각, 타임아웃이 반드시 발생한다.
   → 모델 출력은 **검증기를 통과해야만** 액추에이터에 도달한다.
   안전 한계는 **MCU 펌웨어에 하드코딩**하며 모델이 넘을 수 없다.

## 1. 스택 구조 (수평 계층)

```
┌─────────────────────────────────────────────────────────┐
│ L5  관측 · 평가    결정 로그, 골든셋, 재현            │
├─────────────────────────────────────────────────────────┤
│ L4  오케스트레이션 정책 루프, 안전, 기술 기록·보관     │
├─────────────────────────────────────────────────────────┤
│ L3  추론          Local VLM/LLM, 구조화 출력          │
├─────────────────────────────────────────────────────────┤
│ L2  인지          카메라, 센서 → 관측(observation)    │
├─────────────────────────────────────────────────────────┤
│ L1  장치 추상화    역량 계약(capability contract)      │
├─────────────────────────────────────────────────────────┤
│ L0  하드웨어·전송  Arduino/ESP32, serial/SPI/WiFi     │
└─────────────────────────────────────────────────────────┘
```

**계층 규칙:** 각 계층은 **아래 계층 없이 테스트 가능**해야 한다.
가짜 프레임 소스, 가짜 MCU(loopback)를 항상 제공한다.
카메라가 없어도 L3~L5를 개발할 수 있어야 하며, 이것이 현재 상황에서 특히 중요하다.

## 2. 수직 슬라이스 (Vertical Stackable)

각 슬라이스는 **모든 계층을 관통하는 얇은 종단 경로**이며,
그 자체로 **데모 가능**하고, 다음 슬라이스의 **토대가 된다**.
슬라이스를 쌓을 뿐 이전 것을 버리지 않는다.

```
VS-6  폐루프 · 안전 · 평가
VS-5  다중 MCU · 다중 액추에이터 · 센서 입력
VS-4  역량 계약 — "프로그램 불필요" 실현
VS-3  VLM 판단 삽입 — 정의서 1번 달성
VS-2  규칙 기반 종단 연결 (AI 없는 베이스라인)
VS-1  인지 경로 확립
VS-0  액추에이터 경로 확립                    ← 완료
```

---

### VS-0 — 액추에이터 경로 ✅ 완료

Jetson → USB serial → Arduino → LED. 프로토콜·툴체인·검증 완료.
산출물: `arduino/led_blink/`, `host/blink.py`, `Makefile`.

---

### VS-1 — 인지 경로 확립

**목표:** "신뢰할 수 있는 프레임"을 상위 계층에 공급한다.

| µ | 내용 | 검증 기준 |
|---|---|---|
| µ1.1 | 카메라 확보 결정 (USB 웹캠 즉시 / IMX219 병행) | `/dev/video*` 생성 |
| µ1.2 | 프레임 취득 → `numpy` 배열 | shape·dtype 일치 |
| µ1.3 | **프레임 건전성 검사** | 아래 참조 |
| µ1.4 | 인지 인터페이스 추상화 + 가짜 소스 | 카메라 없이 상위 계층 테스트 통과 |
| µ1.5 | 캡처 서비스화 (최신 프레임 공유) | 소비자 2개 동시 접근 |

**µ1.3이 이 슬라이스의 핵심이다.** Project 0에서 `/dev/video0`이 존재하고
캡처도 성공했지만 **모든 픽셀이 4100인 평탄 프레임**이었다. 같은 함정을
두 번 밟지 않도록 다음을 자동 검사로 고정한다:

```python
def assert_frame_sane(frame):
    if frame.std() < 1.0:          # 평탄 프레임 (IMX708 사례)
        raise CameraError("flat frame — 센서 미설정 의심")
    if frame.max() == frame.min():
        raise CameraError("constant frame")
```

µ1.4의 가짜 소스가 **임계 경로를 끊는다** — 카메라 배송을 기다리는 동안에도
VS-2 이후를 개발할 수 있다.

---

### VS-2 — 규칙 기반 종단 연결 (베이스라인)

**목표:** AI 없이 카메라→LED 루프를 완성한다. **VS-3의 비교 기준**이 된다.

| µ | 내용 | 검증 기준 |
|---|---|---|
| µ2.1 | 프레임 → 특징 (평균 밝기, HSV 지배 색상) | 색지 4종 판별 |
| µ2.2 | 특징 → LED 명령 매핑 (고정 규칙) | 매핑 테이블대로 동작 |
| µ2.3 | 종단 지연 측정 | 수치 기록 (AI 도입 후 비교용) |
| µ2.4 | 데모: 빨간 물체 → LED 점등 | 육안 확인 |

**왜 AI 없이 먼저 만드는가.** VS-3에서 문제가 생겼을 때
"모델이 틀린 것"과 "배선·프로토콜이 틀린 것"을 **분리**할 수 있어야 한다.
베이스라인이 없으면 모든 실패가 모델 탓으로 오인된다.
또한 µ2.3의 지연 수치는 VLM 도입 비용을 정량화한다.

---

### VS-3 — VLM 판단 삽입 (정의서 1번 달성)

**목표:** 이미지 해석과 제어 결정을 **모델이** 내린다.

| µ | 내용 | 검증 기준 |
|---|---|---|
| µ3.1 | VLM 선정·설치 (8GB 제약) | 추론 성공, 메모리 여유 확인 |
| µ3.2 | **구조화 출력 강제** | 100회 중 스키마 위반 0 |
| µ3.3 | 프롬프트 계약 정의 | 재현 가능 |
| µ3.4 | VS-2와 A/B 비교 | 정확도·지연 표 |
| µ3.5 | 실패 모드 처리 | 아래 참조 |

**µ3.1 — 8GB 제약이 최대 난관이다.** Orin Nano의 8GB는 CPU·GPU 공용이고,
현재 ollama(qwen3.5:9b) + llama-server가 이미 상주 중이다.
VLM을 얹으려면 **기존 모델 언로드 전략이 필요**하다. 양자화(Q4) 기준
7B급 VLM이 약 5~6GB를 쓰므로 동시 상주는 어렵다.
→ 모델 생애주기 관리를 µ3.1의 명시적 산출물로 둔다.

**µ3.2 — 자유 텍스트를 받아 파싱하지 않는다.** JSON 스키마 강제
(ollama `format`, llama.cpp GBNF 문법)로 **디코딩 단계에서** 구조를 보장한다.
사후 파싱은 반드시 깨진다.

**µ3.5 실패 모드와 대응:**

| 실패 | 대응 |
|---|---|
| 스키마 위반 | 검증기가 차단 → 재시도 1회 → 폴백 |
| 타임아웃 | 이전 명령 유지, 안전 상태로 감쇠 |
| 환각 (없는 액추에이터 지시) | 역량 계약 검증에서 거부 (VS-4) |
| 판단 불가 | `"action": "none"` 을 **합법 출력**으로 허용 |

마지막 항목이 중요하다. 모델에게 "모르겠다"는 출구를 주지 않으면 **반드시 지어낸다.**

### VS-4 — 역량 계약 ("프로그램 불필요" 실현)

**목표:** 액추에이터 추가가 **코드 수정 0줄**이 되게 한다.
정의서의 "프로그램 불필요"와 2번 항목("액추에이터 구성은 사용자가 입력")이
실제로 성립하는 지점이며, **이 프로젝트의 아키텍처적 핵심**이다.

| µ | 내용 | 검증 기준 |
|---|---|---|
| µ4.1 | 액추에이터 기술 스키마 정의 (JSON) | 스키마 문서화 |
| µ4.2 | 스키마 → LLM 도구 정의 **자동 생성** | 수기 동기화 불필요 |
| µ4.3 | 명령 검증기 (계약 위반 거부) | 위반 명령 100% 차단 |
| µ4.4 | **새 액추에이터 추가 시험** | **코드 수정 없이 동작** |

스키마 예시:

```json
{
  "id": "led_main",
  "kind": "led",
  "transport": "serial:/dev/ttyACM0",
  "commands": {
    "on":    {"args": {}},
    "off":   {"args": {}},
    "blink": {"args": {"interval_ms": {"type":"int","min":10,"max":5000}}}
  },
  "safety": {"max_duty": 1.0}
}
```

`min`/`max`는 **모델이 넘을 수 없는 경계**다. 동일한 제약을 MCU 펌웨어에도
중복 구현한다 — 호스트 검증은 우회될 수 있지만 펌웨어는 최후 방어선이다.
(Project 0의 `INT 5 → ERR interval must be >= 10`이 이 패턴의 선례다.)

**µ4.4가 이 슬라이스의 합격 판정이다.** 서보 하나를 스키마에만 추가하고
파이썬 코드를 한 줄도 건드리지 않은 채 모델이 그것을 쓸 수 있으면 성공이다.

---

### VS-5 — 다중 MCU · 다중 액추에이터 · 센서

**목표:** 정의서의 하드웨어 범위 전체를 계약 안으로 끌어들인다.

| µ | 내용 | 검증 기준 |
|---|---|---|
| µ5.1 | ESP32 전송 계층 (WiFi/serial) | 계약 스키마 무변경 |
| µ5.2 | 서보 · 스테퍼 구동 | 위치 지령 정확도 |
| µ5.3 | 센서 입력 (조도·소리·연기) → 관측 | L2 인지에 통합 |
| µ5.4 | 다중 장치 라우팅 | 장치 3개 동시 제어 |

µ5.1의 합격 조건은 **전송 계층이 바뀌어도 상위가 모르는 것**이다.
serial이든 WiFi든 L1 계약 위에서는 동일하게 보여야 한다.

µ5.3에서 센서가 들어오면 입력이 이미지 단독에서 **다중 모달**로 확장된다.
이 시점에 관측 포맷을 재설계하지 않도록, L2 인지 인터페이스를 µ1.4에서
처음부터 "관측 = {이미지, 센서값, 타임스탬프}"로 정의해 둔다.

---

### VS-6 — 폐루프 · 안전 · 평가

**목표:** 시연 수준에서 **운용 가능 수준**으로 올린다.

| µ | 내용 | 검증 기준 |
|---|---|---|
| µ6.1 | 안전 인터록 (MCU 하드 리밋) | 호스트가 위반 명령을 보내도 차단 |
| µ6.2 | 워치독 | 호스트 단절 시 안전 상태 전이 |
| µ6.3 | 골든셋 평가 (이미지 → 기대 명령) | 회귀 자동 탐지 |
| µ6.4 | 결정 로그 · 재현 | 임의 결정 1건 재현 가능 |

µ6.2는 실물 액추에이터에서 **필수**다. LED는 무해하지만 스테퍼 모터는
호스트가 죽은 사이 계속 돌면 기구를 파손한다. MCU가 일정 시간
명령을 못 받으면 스스로 정지해야 한다.

µ6.3의 골든셋이 없으면 프롬프트를 고칠 때마다 **무엇이 나빠졌는지 알 수 없다.**
VS-3 완료 직후부터 이미지·기대출력 쌍을 모으기 시작한다.

### 3.2 ADR (Architecture Decision Record)

되돌리기 어려운 결정마다 1파일. 형식은 최소로 유지한다:

```markdown
# ADR-0001 — 타이밍은 MCU가 소유한다
상태: 채택   날짜: 2026-09-16
## 배경
## 결정
## 근거
## 대안과 기각 사유
## 결과 (파급 효과)
```

**이미 확정된 ADR 후보 (VS-1 착수 시 문서화):**

| ID | 결정 | 근거 |
|---|---|---|
| 0001 | 타이밍은 MCU, 의도는 호스트 | USB 지연·스케줄링으로 호스트 타이밍 불가 (VS-0 실증) |
| 0002 | 모델 출력은 스키마 강제 디코딩 | 사후 파싱은 필연적으로 실패 |
| 0003 | 안전 한계는 펌웨어에 중복 구현 | 호스트 검증은 우회 가능 |
| 0004 | 인지 계층 인터페이스 추상화 | 카메라 교체가 상위에 전파되지 않도록 |
| 0005 | 카메라는 존재가 아니라 픽셀로 검증 | IMX708 사례 (project_0) |

### 3.3 기록 원칙

- **실패를 남긴다.** 무엇을 시도했고 왜 안 됐는지가 더 비싼 정보다.
  `project_0_camtest.md`의 "소거된 변수" 표가 그 예다.
- **소거된 변수를 명시한다.** 다음 사람이 같은 실험을 반복하지 않도록.
- **수치를 남긴다.** "느리다"가 아니라 "종단 지연 2.4초".
- **재현 명령을 남긴다.** 결론뿐 아니라 그것을 얻은 명령을 함께.

### 3.4 RAG 연동 (선택, VS-4 이후)

이미 구동 중인 스택을 프로젝트의 **기술 기억**으로 전환할 수 있다:

```
docs/tech/*.md ──> bge-m3 (임베딩, :11434)
                       │
                  벡터 색인
                       │
                  bge-reranker (:8083)
                       │
                  qwen3.5:9b ──> "이 액추에이터 왜 이렇게 설계했나?"
```

기록이 문서에 머무르지 않고 **시스템 자신이 질의 가능한 자산**이 된다.
정의서의 "독립적인 환경"과도 일치한다 — 전부 온디바이스다.

## 4. 임계 경로와 병행 가능 작업

```
임계 경로:  카메라 확보 ──> VS-1 ──> VS-2 ──> VS-3
병행 가능:  µ1.4 가짜 소스 ──> VS-4 설계 ──> ADR 작성 ──> µ3.1 VLM 선정
```

**카메라 없이 지금 진행 가능한 것:**

1. µ1.4 — 인지 인터페이스 + 가짜 프레임 소스 (임계 경로를 끊는 작업)
2. µ3.1 — VLM 선정 및 8GB 메모리 전략 수립 (최대 난관, 조기 착수 가치 높음)
3. VS-4 — 역량 계약 스키마 설계 (순수 설계, 하드웨어 무관)
4. ADR 0001~0005 문서화

**권장 착수 순서:** µ1.4 → µ3.1 → VS-4 설계 → (카메라 도착) → VS-1 → VS-2 → VS-3

µ3.1을 앞당기는 이유는 8GB 제약이 **아키텍처를 바꿀 수 있는** 유일한 미지수이기
때문이다. VLM이 안 올라가면 VS-3 전체 설계를 다시 해야 한다
(예: 경량 비전 모델 + 텍스트 LLM 분리). 늦게 발견할수록 비싸다.

## 5. 리스크

| 리스크 | 영향 | 완화 |
|---|---|---|
| **8GB에 VLM 미탑재** | VS-3 재설계 | µ3.1 조기 착수. 대안: 경량 비전(검출·분류) + 텍스트 LLM 분리 |
| 카메라 조달 지연 | 임계 경로 정체 | µ1.4 가짜 소스로 병행. USB 웹캠 즉시 투입 |
| VLM 지연 과다 | 실시간성 훼손 | 정책/제어 루프 분리 (이미 설계). 판단 주기를 초 단위로 낮춤 |
| 모델 출력 불안정 | 오동작 | 스키마 강제 + 검증기 + 펌웨어 한계 (3중) |
| JetPack 패키지 파손 | 환경 붕괴 | `apt upgrade` 시 `nvidia-l4t-*` 제거 여부 사전 확인 |
| 액추에이터 물리 손상 | 하드웨어 손실 | µ6.1 인터록, µ6.2 워치독을 모터 투입 **이전에** 구현 |

마지막 항목의 순서를 지킨다. 스테퍼 모터를 먼저 붙이고 안전장치를 나중에
만들면, 그 사이의 실수 한 번이 기구를 부순다.
