# 강사용 해설서

학습자용 실습서(`01`~`06`)와 짝을 이룬다. 연습 문제 해답, 학습자가 막힐 지점,
모듈마다 무엇을 강조할지를 담았다.

---

## 1. 이 교재의 설계 의도

### 가르치려는 것은 기술이 아니라 판단이다

LED 를 깜빡이는 방법은 검색하면 나온다. 이 교재가 가르치려는 것은
**"동작한다" 고 언제 말할 수 있는가** 이다.

그래서 모든 모듈이 같은 형태를 갖는다 — 성공처럼 보이는 신호를 주고,
그것이 거짓임을 학습자가 **스스로 발견**하게 한다.

| 모듈 | 거짓 성공 신호 |
|---|---|
| 0 | `/dev/video0` 이 생기고 캡처도 성공 |
| 1 | 점멸이 되긴 된다 (불규칙할 뿐) |
| 2 | 테스트가 통과한다 (추상화를 깨기 전까지) |
| 3 | LED 가 반응한다 (떨릴 뿐) |
| 4 | 30 fps 로 잘 돈다 (VLM 이 80% 실패 중) |
| 5 | 선언이 적재된다 (실물은 없음) |

**이 반복이 의도적이다.** 여섯 번 다른 층위에서 같은 일을 겪으면 원칙이 남는다.

### 세 주제의 배치

- **주제 A (성공 신호 ≠ 동작)** — 모듈 0 에서 충격적으로, 이후 매 모듈에서 재확인
- **주제 B (측정하지 않은 것은 모른다)** — 모듈 3 에서 기준선을 재고, 모듈 4 에서
  그 기준선이 판단을 바꾸는 것을 본다
- **주제 C (느린 것과 빠른 것 분리)** — 모듈 1(타이밍) → 3(이력) → 4(비동기)로
  **같은 원리를 점점 추상적인 층위에서** 만난다

모듈 4 에서 "이거 모듈 1 이랑 같은 얘기 아닌가요?" 라는 질문이 나오면 성공이다.
그때 명시적으로 연결해 준다.

## 2. 운영 지침

### 시간 배분

| 모듈 | 실습서 표기 | 실제 권장 | 비고 |
|---|---|---|---|
| 준비 | — | 60분 | 부품 확인·환경 구축. **사전 과제 권장** |
| 0 | 90분 | 120분 | 재부팅 2~3회가 필수라 시간이 든다 |
| 1 | 120분 | 120분 | 배선 실수가 잦다 |
| 2 | 90분 | 90분 | 순수 소프트웨어라 예측 가능 |
| 3 | 120분 | 150분 | 조명 환경에 따라 임계값 조정 필요 |
| 4 | 180분 | **2회 분할** | llama.cpp 빌드 30분을 쉬는 시간에 |
| 5 | 90분 | 90분 | |

**총 12~14시간.** 2일 집중 과정 또는 주 1회 6~7주.

### 사전 준비 (강사)

1. **llama.cpp 빌드와 모델 내려받기를 미리 해 둔다.** 30분 빌드 + 2.6GB 다운로드를
   수업 중에 하면 시간이 녹는다. 미리 빌드한 이미지나 압축본을 배포하는 편이 낫다.
2. **고장난 카메라를 하나 준비한다.** 모듈 0 의 핵심 경험(평탄 프레임)을 재현하려면
   IMX708 모듈이 하나 있으면 좋다. 없으면 `flat()` 페인터로 대체하되,
   **실물로 겪는 것과 체감이 다르다**는 점은 감안한다.
3. **공통 저항 LED 와 개별 저항 LED 를 둘 다 준비한다.** 모듈 1 의 전류 경쟁
   실습에 필요하다. 없으면 브레드보드에서 저항을 하나로 합쳐 재현할 수 있다.

### 조별 편성

**2인 1조를 권한다.** 한 명이 명령을 치고 한 명이 LED·화면을 본다.
혼자 하면 타이밍 실습(모듈 1)에서 떨림을 관찰하기 어렵다.

## 3. 모듈별 해설

### 모듈 0 — 하드웨어 진실

#### 강조할 것

`-121` 이 무엇인지 반드시 짚는다. 학습자는 오류 번호를 "그냥 안 된다" 로 읽는다.

> `-121` = `EREMOTEIO` = **i2c NACK**.
> 드라이버도 정상, 버스도 정상, **아무도 대답하지 않았을 뿐**이다.

이 구분이 진단의 출발점이다. "안 된다" 와 "이 계층까지는 정상이고 여기서 끊겼다"
는 완전히 다른 정보다.

#### 학습자가 막힐 지점

| 증상 | 원인 | 대응 |
|---|---|---|
| `config-by-hardware.py` 가 실패 | 헤더 번호 생략 | `-n 2="..."` 로 지정 |
| 재부팅해도 `/dev/video*` 없음 | 오버레이 미적용 | `grep OVERLAYS /boot/extlinux/extlinux.conf` |
| `i2ctransfer` 가 응답 없음 | 스트리밍 중이 아님 | 센서는 INCK 클럭이 있어야 답한다 |
| 권한 거부 | `i2c` 그룹 | `-f` 옵션 또는 그룹 추가 |

**가장 흔한 질문:** "케이블을 다시 꽂아볼까요?"
→ 여기서 멈추게 하고 되묻는다. **"케이블이 원인이라면 로그가 어떻게 달라야 하죠?"**
오버레이가 없으면 i2c 버스 자체가 없다. 케이블은 그 다음 문제다.

#### 연습 문제 해답

**1. `/dev/video0` 이 있는데 고장났음을 증명하는 가장 짧은 절차**

```bash
gst-launch-1.0 -q nvarguscamerasrc num-buffers=60 ! nvvidconv ! jpegenc ! \
  multifilesink location=/tmp/f_%03d.jpg
python3 -c "
import cv2, numpy as np
img = cv2.imread('/tmp/f_059.jpg')
print(img.min(), img.max(), img.std())"
```
`min == max` 또는 `std ≈ 0` 이면 고장. **핵심은 픽셀을 보는 것**이며,
장치 노드·드라이버 로그·캡처 성공 여부는 모두 답이 아니다.

*채점 포인트:* 프레임 통계를 확인하는가. `ls` 나 `v4l2-ctl --list-devices` 로
끝내면 이 모듈의 요지를 놓친 것이다.

**2. `-121` 과 `invalid sensor model id` 의 차이**

| | 정상인 범위 | 끊긴 지점 |
|---|---|---|
| `-121` | 드라이버·i2c 버스·전원 | **센서가 응답 자체를 안 함** |
| `invalid sensor model id` | 위 전부 **+ i2c 통신 성공** | 응답한 칩이 기대한 모델이 아님 |

즉 `invalid model id` 가 **더 진전된 상태**다. 통신은 됐다.
이 경우 다른 센서가 같은 주소를 쓰고 있을 가능성이 높다.

*채점 포인트:* "둘 다 오류" 가 아니라 **어디까지 정상인지**를 구분하는가.

**3. 소프트웨어 장애에 적용한다면**

`/health` 가 ok 를 반환해도 서비스가 요청을 처리한다는 보장이 없다.
헬스 체크가 프로세스 생존만 확인하고 의존성(DB·모델·디스크)을 확인하지 않으면
같은 함정이다. **모듈 4 에서 llama-server 로 정확히 이것을 겪는다** — 미리
예고해 두면 연결이 선명해진다.

*모범 답안 확장:* "헬스 체크는 실제 작업의 축소판이어야 한다" 까지 나오면 훌륭하다.

### 모듈 1 — 타이밍 소유권

#### 강조할 것

**(a) 와 (b) 를 반드시 눈으로 비교시킨다.** 설명으로 넘어가면 안 된다.
100ms 주기에서 호스트 주도의 떨림은 명확히 보이고, 이 체감이 이 모듈의 전부다.

떨림이 잘 안 보이면 **50ms 로 낮춘다.**

#### 학습자가 막힐 지점

| 증상 | 원인 |
|---|---|
| 포트 권한 거부 | `dialout` 그룹 미적용 — 재로그인 필요 |
| 업로드 실패 | 시리얼 모니터가 포트를 쥐고 있음 |
| LED 가 아예 안 켜짐 | 극성(공통 애노드) 또는 저항 누락 |
| 흰색이 주황빛 | 공통 저항 — 정상 증상 |
| 첫 명령이 무시됨 | 포트 열기가 DTR 로 보드를 리셋 |

마지막 항목을 짚어준다. `host/blink.py` 가 `READY` 배너를 기다리는 이유다.
**고정 시간 `sleep` 으로 때우면 느린 날 깨진다.**

#### 연습 문제 해답

**1. 호스트 주도가 떨리는 두 원인과 해결**

| 원인 | 해결 |
|---|---|
| USB CDC 왕복 지연 | 명령 수를 줄인다 — 의도만 보내고 반복은 MCU 가 |
| 리눅스 스케줄러 지터 (`sleep` 부정확) | 실시간 커널·우선순위로 **완화**는 되나 제거 불가 |

**핵심은 두 번째가 근본적으로 해결되지 않는다는 점이다.** 범용 OS 에서
마이크로초 정밀도를 기대할 수 없다. 그래서 타이밍을 MCU 로 옮긴다.

*채점 포인트:* "sleep 을 정확하게 만든다" 로 끝나면 부족하다. 구조를 바꿔야 한다는
결론에 도달하는가.

**2. 호스트가 타이밍을 쥐는 것이 맞는 경우**

`--pattern sos` 처럼 **패턴 자체가 호스트의 의도이고 MCU 가 모르는 경우**.
모스 부호를 펌웨어에 넣으면 패턴을 바꿀 때마다 재플래싱해야 한다.

일반화하면: **정밀도 요구가 낮고(수백 ms) 변경이 잦은 것**은 호스트,
**정밀도 요구가 높고 안정적인 것**은 MCU.

*토론거리:* 이 경계는 어디인가? 정답이 없으므로 조별 토론에 좋다.

**3. 범위 검사를 호스트에만 두면**

- 다른 프로그램이 포트를 열고 임의 문자열 전송 → 검사 우회
- 호스트 코드의 버그가 곧바로 하드웨어 손상
- **모듈 4 이후 AI 가 명령을 만들면** 환각이 직접 하드웨어에 닿는다

구체 사고 예: 서보에 범위를 넘는 각도를 보내 기구가 물리적 한계를 넘어 파손.
LED 는 무해하지만 **모터에서는 되돌릴 수 없다.**

*채점 포인트:* 모듈 6 의 안전 주제를 미리 끌어오는 답이면 우수하다.

### 모듈 2 — 인지 계층

#### 강조할 것

추상화를 **미학이 아니라 일정 관리 도구**로 설명한다. 학습자는 인터페이스 분리를
"좋은 코드" 정도로 이해하고 넘어가기 쉽다.

> 부품이 일주일 뒤 도착한다. 그동안 무엇을 할 수 있는가?

이 질문으로 시작하면 동기가 선명해진다.

#### 학습자가 막힐 지점

- **`v4l2:0` 으로 CSI 를 읽으려다 멈춤** — 의도된 실습이지만 무한 대기라
  당황한다. `Ctrl-C` 를 미리 알려준다.
- **합성 소스가 단색인데 검사를 통과하는 것**에 혼란. `solid()` 가 노이즈를
  섞는다는 점을 짚어준다. 순수 단색을 원하면 `flat()` 이고 그것은 막힌다.

#### 연습 문제 해답

**1. 임계 경로를 끊는다는 의미**

일정에서 **가장 긴 의존 사슬**이 임계 경로다. 카메라 → 인지 → 판단 → 구동 이
직렬로 묶여 있으면 카메라 배송이 전체를 막는다.

합성 소스가 인지 계층을 **대체**하면 판단·구동 개발이 카메라와 병렬이 된다.
배송 일주일이 전체 일정에서 사라진다.

*채점 포인트:* "테스트하기 좋다" 가 아니라 **일정이 단축된다**는 관점이 나오는가.

**2. `sensors` 슬롯을 처음부터 넣은 이유**

모듈 6(VS-5)에서 조도·소리·연기 센서가 들어온다. 그때 `Observation` 에 필드를
추가하면 **모든 소비자를 고쳐야 한다.** 지금 비어 있는 dict 하나를 두는 비용은
거의 0 이고, 나중에 추가하는 비용은 크다.

*주의:* 이것을 "미래를 위한 과잉 설계" 와 구분해 가르쳐야 한다.
차이는 **그 미래가 계획서에 적혀 있는가** 이다. 근거 없는 확장점은 오히려 해롭다.

**3. RGB 통일과 경계 변환**

cv2 는 BGR, PIL·VLM 은 RGB 를 기대한다. 변환 시점을 소비자에게 맡기면
각 소비자가 "이게 무엇인지" 기억해야 한다.

**생기는 버그:** 채널이 뒤바뀌어도 **프로그램이 죽지 않는다.** 빨강이 파랑으로
보일 뿐이다. 그래서 발견이 늦고, VLM 입력에서는 "모델이 색을 못 맞힌다" 로
오인된다.

*채점 포인트:* **조용히 실패한다**는 성질을 짚는가. 크래시하는 버그보다 나쁘다.

### 모듈 3 — 규칙 기반 폐루프

#### 강조할 것

**자동노출 실습이 이 모듈의 정점이다.** 시간이 부족하면 다른 것을 줄이고
이것을 지킨다.

`전역 차이 +0.02` 를 보여준 뒤 묻는다:
> **"카메라가 LED 를 못 보는 걸까요?"**

학습자 다수가 "못 본다" 고 답한다. 그 다음 국소 최대 `+57.5` 를 보여준다.
**측정 방법이 결론을 바꾼다**는 것을 체감하는 순간이다.

#### 학습자가 막힐 지점

- **조명이 어두워 색 판별이 안 됨.** `MIN_SATURATION`·`MIN_VALUE` 를 낮추게 한다.
  임계값이 환경 의존이라는 것 자체가 배울 점이다.
- **`--lock` 을 빼먹고 결과가 흔들림.** AWB 가 색을 재해석한다.
- **이력 실습에서 차이를 못 느낌.** 장면을 완전히 정지시켜야 한다.
  손이 화면에 들어가면 진짜 변화가 생겨 구분이 안 된다.

#### 연습 문제 해답

**1. 판단 0.0ms 가 왜 중요한 측정값인가**

그 자체로는 의미가 없다. **모듈 4 의 비교 기준**이기 때문에 중요하다.

VLM 도입 후 판단이 1000ms 가 되면, 0.0 → 1000 이라는 **차이가 곧 AI 의 비용**이다.
기준선이 없으면 "느리다" 는 말밖에 못 하고, 그 느림이 감당 가능한지 판단할 수 없다.

*채점 포인트:* "빠르다" 가 아니라 **비교 기준**이라는 답이 나오는가.

**2. AE 상쇄가 야간등 규칙에서 우연한 안전이 되는 이유**

"어두우면 LED 를 밝게" 규칙에 양의 되먹임 위험이 있다 — LED 를 켜면 밝아지고,
밝아지면 LED 를 끄고, 어두워지면 다시 켜는 발진.

AE 가 전역 밝기를 상쇄하므로 LED 를 켜도 **측정 밝기가 거의 안 변하고**,
따라서 발진이 생기지 않는다.

**의존하면 안 되는 이유:** 이것은 설계가 아니라 부작용이다.
AE 를 고정(`aelock`)하는 순간 사라진다. 그리고 모듈 4 에서 실제로 고정한다.
**안전은 우연이 아니라 설계로 확보해야 한다.**

*채점 포인트:* 후반부(의존 금지 이유)까지 도달하는가.

**3. 이력 vs 이동평균**

| | 이력 | 이동평균 |
|---|---|---|
| 노이즈 억제 | ✅ | ✅ |
| 진짜 변화에 대한 반응 | **즉시** | **지연** |
| 경계 진동 | 없음 | 없음 |
| 적합한 상황 | 변화가 드물고 급격 | 변화가 연속적 |

이 용도에서는 색이 **드물게, 급격히** 바뀐다(물체를 바꿔 드는 순간).
이동평균은 그 전환을 뭉갠다. 이력은 임계를 넘는 순간 바로 따라간다.

*확장 질문:* 온도 센서였다면 어느 쪽이 맞을까? (이동평균)

### 모듈 4 — 온디바이스 AI

#### 강조할 것

**측정 방법이 결론을 뒤집는 사례**를 두 번 보여준다.

1. "7B 가 올라가나?" — 단독으로 재면 **된다**, 운용 조건에서 재면 **안 된다**
2. "VLM 이 잘 동작하나?" — 화면은 30fps 로 멀쩡, 통계는 **80% 실패**

두 번째가 특히 중요하다. **폴백이 증상을 가린다.**

> 여러분의 시스템에서 "잘 돌고 있다" 는 무엇을 근거로 하는 말입니까?

#### 학습자가 막힐 지점

| 증상 | 원인 |
|---|---|
| 빌드 중 OOM | `-j6` → `-j4` |
| 서버가 첫 요청에 죽음 | `--parallel 1` 누락 |
| `GGML_ASSERT(n_tokens_all...)` | 이미지가 너무 큼 → 768×432 |
| 컨텍스트를 줄였더니 더 깨짐 | **직관 반대** — 이미지 토큰이 배치에 들어가야 함 |
| 모델이 엉뚱한 답 | 프롬프트보다 **조명**을 먼저 의심 |

마지막 항목: 어두운 장면에서 모델은 `none` 을 반환한다. **이것은 정상 동작**이며
모델 성능 문제가 아니다. 학습자가 프롬프트를 고치기 시작하면 멈추게 한다.

#### 연습 문제 해답

**1. "7B 가 올라간다" 를 반증하려면**

**운용 조건 전체를 동시에 돌리면서** 재야 한다:
- llama-server 상주
- 카메라 파이프라인 가동 (`nvargus-daemon` + ArgusSource)
- 제어 루프 실행
- **그 상태에서 실제 추론 요청**

측정할 것: 가용 메모리 최저값, 스왑 사용량, **요청 성공 여부**.

핵심은 **적재 성공이 아니라 서빙 성공**을 봐야 한다는 점이다.
7B 는 적재되고, 카메라·루프까지 견디고, **추론 요청에서 죽는다.**
앞 두 단계만 재면 틀린 결론에 도달한다.

*채점 포인트:* "동시에" 와 "실제 요청" 이 둘 다 나오는가.

**2. 폴백의 장단점**

| 장점 | 위험 |
|---|---|
| 첫 판단 전에도 동작 | **실패를 가린다** |
| VLM 이 죽어도 LED 유지 | "잘 되는 것처럼" 보인다 |
| 성능 저하가 점진적 | 성능 저하를 **눈치채지 못한다** |

대응: **통계를 반드시 노출한다.** `policy.stats` 의 `failed`/`invalid` 를
로그·대시보드에 올리고, 임계를 넘으면 경보한다.

일반 원칙: **우아한 성능 저하(graceful degradation)는 관측 가능해야 한다.**
조용한 폴백은 장애를 은폐한다.

*채점 포인트:* 위험 쪽을 인식하는가. 장점만 쓰면 절반이다.

**3. `none` 이 유지 vs `off` 전송**

`none` = "판단 불가", `off` = "끄라는 판단". **완전히 다른 의미**다.

사고 예시:
- **조명이 잠깐 깜빡여** 한 프레임이 어두워짐
- `none` → 직전 상태 유지 → 아무 일 없음
- `off` 로 처리 → **경고등이 꺼진다**

모터라면 더 나쁘다. 판단 불가마다 정지하면 기구가 덜컥거리고, 최악의 경우
안전 위치가 아닌 곳에서 멈춘다.

**일반 원칙:** 판단 실패의 기본 동작은 "아무것도 하지 않음" 이어야지
"특정 동작을 수행" 이면 안 된다. 다만 **안전 정지가 필요한 경우는 예외**이며,
그 구분은 도메인이 정한다 — 모듈 6 의 워치독 주제로 연결된다.

*채점 포인트:* 구체적 사고 시나리오를 제시하는가.

### 모듈 5 — 역량 계약

#### 강조할 것

**해시 확인을 반드시 시킨다.** `md5sum` 을 전후로 찍는 이 절차가 이 모듈의 증명이다.
"코드를 안 고쳤다" 는 주장이 아니라 **검증 가능한 사실**이 된다.

그리고 모듈 4 의 계약 분기 사고와 명시적으로 연결한다:

> 모듈 4 에서는 **규율**로 막으려다 실패했다. 여기서는 **구조**로 막는다.
> 적을 곳이 하나뿐이면 갈라질 수 없다.

#### 학습자가 막힐 지점

- **JSON 문법 오류** — 후행 콤마가 가장 흔하다. 오류 메시지가 파일명을 포함하도록
  `Registry.load` 가 감싸고 있다는 점을 알려준다.
- **`wire` 템플릿의 `{}` 와 JSON 이스케이프 혼동** — `\n` 을 JSON 안에서 어떻게
  쓰는지 짚어준다.
- **"이게 왜 좋은 거죠?"** — 장치가 하나일 땐 실감이 안 난다.
  **반드시 두 번째 장치를 추가시켜야** 가치가 보인다.

#### 연습 문제 해답

**1. `wire` 가 없다면**

선언은 "무엇을 할 수 있는가" 만 말하고 **"어떻게 보내는가" 를 말하지 못한다.**
그러면 장치마다 파이썬 어댑터가 필요하다:

```python
class BuzzerAdapter:
    def beep(self, hz, ms): self.port.send(f"BEEP {hz} {ms}")
```

즉 **장치 추가 = 코드 작성**이 되어 명제가 거짓이 된다.

*확장:* `wire` 의 한계도 논의할 가치가 있다. 단순 치환으로 표현 못 하는
프로토콜(바이너리, 체크섬, 상태 기반)에는 부족하다. 그때는 전송 방식(`transport.type`)
단위로 처리기를 추가한다 — **장치마다가 아니라 프로토콜마다**이므로 확장성이 유지된다.

**2. 선언에 범위가 있는데 펌웨어에도 두는 이유**

선언은 **데이터**이므로:
- 잘못 적힐 수 있다 (오타, 펌웨어 변경 후 미갱신)
- 누구나 고칠 수 있다 (검토 없이)
- 호스트를 거치지 않는 경로가 있다 (`make monitor`, 다른 프로그램)

**펌웨어는 물리적 경계에 가장 가깝고, 우회 경로가 없다.**

비유: 선언은 "이 문으로 들어오세요" 라는 안내문이고,
펌웨어는 **잠긴 문**이다. 안내문이 틀려도 문은 잠겨 있다.

*채점 포인트:* "이중 검사" 가 아니라 **신뢰 수준이 다르다**는 점을 짚는가.

**3. 구조적으로 막는 이유**

모듈 4: 계약이 **두 곳**(스키마, 검증기)에 있었다 → 사람이 동기화해야 함 →
한쪽만 고쳐짐 → 갈라짐.

모듈 5: 계약이 **한 곳**(선언)에 있고 스키마·검증기·전송이 **파생**된다 →
갈라질 대상이 없음.

**일반 원칙:** 같은 사실을 두 번 적어야 한다면, 둘 중 하나를 다른 하나에서
**생성**하라. 생성할 수 없다면 **일치를 검사하는 테스트**를 둬라
(모듈 4 의 `test_schema_and_validator_agree` 가 후자다).

*채점 포인트:* "규율 vs 구조" 의 대비가 나오면 우수하다.

## 4. 자주 나오는 오개념

| 오개념 | 교정 |
|---|---|
| "오류가 없으면 동작하는 것" | 오류 없이 잘못된 결과가 나오는 경우가 더 위험하다 (평탄 프레임, 80% 거부) |
| "더 큰 모델이 더 좋다" | 이 작업에서 3B 가 7B 보다 빠르고, 정확도는 같고, 유일하게 동작한다 |
| "AI 가 판단하니 규칙은 필요 없다" | 규칙 정책은 기준선이자 폴백이다. 둘 다 있어야 한다 |
| "테스트가 통과하니 배포 가능" | 모듈 4 의 80% 거부는 테스트를 통과했다. 통계를 봐야 했다 |
| "추상화는 나중에 하면 된다" | 합성 소스가 없었다면 카메라 배송 일주일을 그대로 잃었다 |
| "검증은 중복이니 한 곳만" | 우회 경로가 다르면 중복이 아니다 |

## 5. 평가 기준

### 실습 평가 (모듈별)

각 모듈 끝에 **"동작을 증명하시오"** 를 요구한다. 산출물이 아니라 **증명 방법**을 본다.

| 수준 | 기준 |
|---|---|
| 미흡 | 화면에 뭔가 나오는 것으로 증명했다고 함 |
| 보통 | 로그·상태를 확인함 |
| **우수** | **출력을 직접 측정**하고, 실패 조건도 함께 확인함 |

### 종합 과제 제안

> **새 액추에이터를 하나 고르고, 모듈 0~5 의 원칙을 적용해 통합하시오.**
> 제출물: 선언 파일, 측정 기록, 실패했던 것과 그때 무엇을 쟀는지.

**"잘 됐습니다" 만 있는 보고서는 감점한다.** 이 교재의 요지는 그 반대다.
