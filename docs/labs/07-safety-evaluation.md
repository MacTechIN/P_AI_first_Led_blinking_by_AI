# 모듈 6 — 확장 · 안전 · 평가

**소요** 약 150분   **선행** 모듈 5   **슬라이스** VS-5, VS-6

> **이 모듈의 절반은 부품을 기다리고 있다.**
> 아래에서 ✅ 로 표시한 부분은 이 기계에서 실제로 구현하고 검증했다.
> ⏸ 는 **실물 하드웨어가 도착해야 검증되는 부분**이다. 시뮬레이션으로
> 연습할 수 있는 것과 실물에서 확인해야 하는 것을 구별해 적었다.
> 검증하지 않은 절차를 검증한 것처럼 적지 않는 것이 이 교재의 원칙이다 (모듈 0).

## 목표

액추에이터가 **무해한 LED 에서 되돌릴 수 없는 모터로** 바뀔 때 무엇이 달라지는지
안다. 그리고 판단 품질이 나빠진 것을 **사람 눈이 아니라 자동으로** 알아차린다.

## 1. ✅ 워치독 — 호스트가 죽으면 어떻게 되는가

### 왜 LED 에는 없어도 되고 모터에는 필수인가

호스트 프로세스가 명령을 보내고 죽었다고 하자.

| 장치 | 결과 |
|---|---|
| LED | 계속 켜져 있다. **아무 일도 일어나지 않는다** |
| 서보 | 마지막 각도를 유지한다. 부하가 걸려 있으면 계속 밀어붙인다 |
| 스테퍼 | 회전 중이었다면 **계속 돈다.** 기구가 한계에 부딪혀 파손된다 |

그래서 워치독은 **모터를 붙이기 전에** 만들어야 한다. 붙이고 나서 만들면,
그 사이의 실수 한 번이 기구를 부순다.

### 실습

```bash
python3 -c "
import sys, time; sys.path.insert(0,'host')
from blink import Arduino
with Arduino('/dev/ttyACM0', verbose=False) as a:
    print('기본:', a.send('STATE'))
    a.send('WATCHDOG 1000'); a.send('RGB 255 0 0'); a.send('ON')
    print('설정 직후:', a.send('STATE'))
    print('... 2.5초 침묵 ...'); time.sleep(2.5)
    a.ser.reset_input_buffer()
    print('대기 후:', a.send('STATE'))
"
```

**예상 출력:**
```
기본:      STATE ON ... watchdog=0 tripped=0
설정 직후:  STATE ON ... watchdog=1000 tripped=0
대기 후:   STATE OFF ... watchdog=1000 tripped=1
```

`STATE OFF` + `tripped=1` — **스스로 안전 상태로 갔다.**

### 설계에서 한 번 틀렸던 것

처음 구현에서 모든 명령이 트립 플래그를 지우게 했다. 그랬더니
**트립을 확인하려고 보낸 `STATE` 가 트립을 먼저 지워서** 플래그를 영영 읽을 수 없었다.

```
대기 후: STATE OFF ... tripped=0      ← 안전 상태인데 트립이 0
```

수정: **모든 명령이 워치독을 먹이되, 출력을 바꾸는 명령만 트립을 해제한다.**
`PING`·`STATE` 는 먹이기만 한다.

의미도 이쪽이 맞다 — 트립된 장치는 호스트가 **명시적으로 다시 명령할 때까지**
안전 상태에 머물러야 한다. "안녕" 이라고 말했다고 모터가 다시 돌면 안 된다.

```bash
python3 -c "
import sys; sys.path.insert(0,'host')
from blink import Arduino
with Arduino('/dev/ttyACM0', verbose=False) as a:
    a.send('WATCHDOG 500'); import time; time.sleep(1.2)
    a.ser.reset_input_buffer()
    print('PING 후:', a.send('PING'), '|', a.send('STATE')[:40])
    print('ON 후  :', a.send('ON'), '|', a.send('STATE')[:40])
    a.send('WATCHDOG 0'); a.send('OFF')
"
```
`PING` 은 트립을 남기고, `ON` 이 해제한다.

### 안전 상태란 무엇인가

장치마다 다르다. **각 장치가 스스로 정의해야 한다.**

| 장치 | 안전 상태 |
|---|---|
| LED | 소등 |
| 서보 | 알려진 중립 위치, 또는 **현재 위치 유지 후 토크 해제** |
| 스테퍼 | 코일 전원 차단 |
| 히터 | 즉시 차단 |

⚠️ **서보의 "안전" 은 자명하지 않다.** 중립으로 급히 돌아가는 것이 오히려 위험할 수
있다(물건을 치거나, 사람 손을 밀거나). 도메인이 정해야 한다.

## 2. ✅ 골든셋 평가 — 나빠진 것을 자동으로 안다

### 문제

프롬프트를 고치거나 모델을 바꾸거나 임계값을 만지면 **무언가는 좋아지고 무언가는
나빠진다.** 눈으로 확인하면 좋아진 것만 보인다.

### 골든셋 만들기

이미지와 기대 출력의 쌍을 모은다. `golden/cases.json`:

```json
[
  {"name": "red LED", "image": "red.jpg",
   "expect": {"colour": "red", "action": "on"},
   "note": "LED 를 hue 0 (#ff0000) 로 켜고 촬영"},
  {"name": "LED 소등", "image": "dark.jpg",
   "expect": {"action": "off"},
   "note": "색 있는 물체가 없다. 지어내면 실패다."}
]
```

**`note` 를 반드시 적는다.** 몇 주 뒤 실패했을 때 "이 사례가 무엇을 지키려
했는지" 를 알아야 고칠 수 있다.

### 실행

```bash
./host/evaluate.py
echo "종료코드: $?"
```

종료코드가 0 이 아니면 회귀다. **CI 에 그대로 걸 수 있다.**

### 실제로 무엇을 찾았나

처음에는 `colour` 만 기대값에 적었다. 결과는 **5/5 통과**였다.

그런데 출력을 자세히 보니:

```
PASS  red LED     {"action": "none", "colour": "red", ...}
PASS  yellow LED  {"action": "off",  "colour": "yellow", ...}
```

색은 맞혔지만 **행동이 틀렸다.** 기대값에 `action` 을 적지 않았으므로 통과한 것이다.

`action` 도 고정하고 다시 돌렸다:

```
FAIL  red LED      action='none'(기대 'on')
PASS  green LED
FAIL  blue LED     action='none'(기대 'on')
FAIL  yellow LED   action='off'(기대 'on')
PASS  LED 소등
2/5 통과
```

**측정된 약점: 이 모델은 색은 안정적으로 맞히지만 행동 선택이 일관되지 않다.**
같은 장면에서 `on`/`none`/`off` 를 오간다.

> 여기서 **기대값을 느슨하게 되돌려 2/5 를 5/5 로 만들고 싶은 충동**이 든다.
> 그것이 정확히 하면 안 되는 일이다. 골든셋은 통과하라고 있는 것이 아니라
> **알아차리라고** 있는 것이다.

### 부분 일치는 양날이다

적어둔 필드만 검사한다. 그래서:

- **장점** — 판단의 일부만 고정하고 나머지는 자유롭게 둘 수 있다
- **위험** — 적지 않은 필드의 회귀는 **조용히 통과한다**

무엇을 고정할지가 곧 **무엇을 지키겠다는 선언**이다.

## 3. 다중 액추에이터와 센서 — 구조는 지금, 실물은 ⏸

### 선언으로 추가한다 (모듈 5)

장치가 늘어도 파이썬은 바뀌지 않는다. 서보 선언은 이미 저장소에 있고,
`status: planned` 로 **실물이 없다고 적혀 있다.**

```bash
python3 -c "
import sys; sys.path.insert(0,'.')
from control.capability import Registry
print(Registry.load().describe())
"
```
→ `servo_pointer (servo) [not wired yet]`

`planned` 인데 전송로가 실제 포트면 **적재 시점에 거부**한다. 선언이 실물보다
먼저 존재해도 살아 있는 하드웨어를 건드릴 수 없다.

### 워치독은 지금 돌려볼 수 있다 (시뮬레이션)

"모터였다면 어땠을까" 를 상상하지 않고 **보면 된다.** 시뮬레이터의 워치독은
펌웨어와 같은 규칙을 따른다 — 모든 명령이 먹이고, **출력을 구동하는 명령만
트립을 푼다.**

```bash
./host/sim_demo.py --still --watchdog 300 --silent-after 20 --steps 60
```

호스트가 20스텝에서 말을 멈추면 300ms 뒤 LED 가 꺼지고 `⚠ 워치독 트립` 이
뜬다. 트립된 뒤에는 `PING` 을 보내도 돌아오지 않는다. 되돌리는 것은 출력을
구동하는 명령뿐이다.

> ⏸ **실물 모터에서의 검증은 아직이다.** 위는 시뮬레이션이고, 의미가 같도록
> 시험으로 고정해 두었다(`tests/test_watchdog_sim.py`). 시뮬레이션에서 맞다는
> 것이 실물에서 맞다는 뜻은 아니다 — 그 구별이 이 교재의 전부다.

### 여기서 드러난 구멍

워치독을 시뮬레이터에 넣자마자 **호스트가 멀쩡한데 트립했다.**

`ControlLoop` 은 명령이 **바뀔 때만** 구동한다(ADR-0007). 정지한 장면에서는
아무것도 나가지 않고, 워치독은 그것을 침묵으로 읽는다. 워치독이 기본으로
꺼져 있어 지금껏 아무도 밟지 않았을 뿐, **실물 코드에도 같은 구멍이 있었다.**

고친 방법: `Actuator.poll()` 을 매 스텝 부른다. 시리얼에서는 `PING` 을 보내고
(먹이되 트립은 풀지 않는다), 시뮬레이터에서는 `world.feed()` 를 부른다.

> **안전장치를 켜면 다른 설계가 따라 바뀐다.** 워치독은 장치에 붙이는 부품이
> 아니라 시스템 전체와 맞물리는 계약이다.

### 실물이 오면 할 일

1. 펌웨어에 `SERVO <angle>` 추가 + **범위 검사** (ADR-0003)
2. 시작 시 `WATCHDOG` 활성화 — 모터이므로 필수
3. **키프얼라이브 주기를 워치독보다 짧게** 설정 (위 구멍 참조)
4. 선언에서 `status`·`note` 제거, `transport` 를 serial 로 변경
5. 안전 상태를 정의하고 펌웨어에 구현
6. 골든셋에 서보 사례 추가

### 센서가 들어오면

`Observation.sensors` 슬롯이 **이미 비어 있는 채로 준비되어 있다** (모듈 2).
포맷을 재설계하지 않아도 된다 — 그 슬롯을 지금 만든 이유가 이것이다.

## 4. 결정 로그와 재현

VLM 판단에는 관측 시각과 시퀀스 번호가 함께 남는다 (`VlmDecision`). 비동기이므로
**판단이 늦게 도착하고**, 어느 프레임을 보고 내린 결정인지 기록하지 않으면
재현할 수 없다.

### 무엇을 남기는가

| 남기는 것 | 없으면 |
|---|---|
| 판단 (action · colour · reason) | 무엇이라 답했는지 모른다 |
| **근거 프레임** | 다시 물어볼 수 없다 |
| 관측 순번과 지연 | 어느 프레임을 보고 내린 결정인지 모른다 |

```python
from control.decisionlog import DecisionLog
log = DecisionLog("decisions")
...
    r = loop.step()
    if r.changed:
        log.record(r, policy.last_decision, note="색지를 바꾼 직후")
```

`StepResult` 가 근거 프레임을 함께 들고 다닌다. 들고 다니지 않으면 재현할 수
없어서 그렇게 바꿨다.

### 이상했던 순간을 사례로 승격한다

```bash
./host/promote_case.py --list                      # 기록된 사건
./host/promote_case.py --changed --to golden/field # 명령이 바뀐 순간을 사례로
./host/evaluate.py --golden golden/field           # 이제 회귀로 돈다
```

현장에서 "LED 가 이상했다" 는 신고를 받으면 **고치기 전에 먼저 고정한다.**
고치고 나서 만들면 무엇을 고쳤는지 증명할 수 없다.

### 승격할 때 결정하는 것

`--fields` 가 **무엇을 지키겠다는 선언**이다. 기본값은 `action,colour` 다.

실습에서 바로 보이는 것 하나: 승격된 사례의 기대값이 `action: "none"` 으로
남을 수 있다. 모델이 기권한 순간을 그대로 적었기 때문이다. 그것이 **관측한
사실**이고, 그대로 두는 것이 맞는지는 사람이 정한다 — 기대값은 "모델이 이렇게
답했다" 가 아니라 "이렇게 답해야 한다" 이기 때문이다. 이 둘을 구별하는 것이
골든셋 작성의 전부다.

## 의도된 실패 실습

1. **워치독을 껐다 켜 본다**: 같은 상황을 두 번 돌린다.
   `./host/sim_demo.py --still --silent-after 20 --steps 60` 은 호스트가 죽어도
   LED 가 계속 켜져 있다. `--watchdog 300` 을 붙이면 꺼진다.
   **이것이 스테퍼였다면** 두 결과가 각각 무엇을 뜻하는지 조별로 서술한다.
2. **트립 플래그 지우기**: 펌웨어에서 `STATE` 도 트립을 해제하도록 되돌린다.
   트립을 관측할 수 없게 되는 것을 확인한다.
3. **골든셋 느슨하게 하기**: `expect` 에서 `action` 을 뺀다. 2/5 가 5/5 가 된다.
   **아무것도 고치지 않았는데** 통과한다.
4. **기대값 없는 사례 추가**: `"expect": {}` 인 사례를 넣는다. 항상 통과한다.
   골든셋에 사례 수를 늘리는 것이 품질을 뜻하지 않음을 본다.

## 교훈

> **안전장치는 그것이 필요한 부품보다 먼저 만든다.**
> **골든셋은 통과하라고 있는 것이 아니라 알아차리라고 있다.**
> 그리고 **검증하지 않은 것을 검증한 것처럼 적지 않는다** — 이 문서의 ⏸ 표시가 그것이다.
> 시뮬레이션에서 맞다는 것은 실물에서 맞다는 뜻이 아니다.
