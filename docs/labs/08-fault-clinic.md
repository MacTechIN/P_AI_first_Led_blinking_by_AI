# 모듈 7 — 진단 클리닉: 증상만 보고 원인을 찾는다

**장비 0원.** 노트북 한 대면 된다. 카메라도 아두이노도 서버도 필요 없다.

지금까지의 실습은 "만들어서 되게 하는 것" 이었다. 이 모듈은 반대다. **이미
고장난 장비를 받아 무엇이 왜 고장났는지 측정으로 밝힌다.** 현장에서 하게 될
일은 대부분 이쪽이다.

## 준비

```bash
./host/sim_demo.py                 # 정상 장비가 어떻게 보이는지 먼저 본다
./host/sim_demo.py --fault list    # 세상에 있는 고장의 종류
```

**정상 상태를 먼저 보는 것이 진단의 절반이다.** 정상을 모르면 이상한 것을
알아볼 수 없다.

## 진행

강사가 팀마다 다른 시드를 준다. **어떤 결함이 들어갔는지는 알려주지 않는다.**

```bash
./host/sim_demo.py --fault random --seed 17 --steps 60
```

화면에 증상 한 줄만 뜬다. 거기서 시작한다.

### 규칙

- `--reveal` 은 **진단 보고서를 제출한 뒤에** 쓴다. 먼저 보면 실습이 끝난다.
- `sim/faults.py` 를 열어보는 것도 같다. 답지를 보는 것이다.
- 쓸 수 있는 것: 측정, 로그, 코드, 지금까지의 실습서, 그리고 `docs/tech/`.

## 진단 절차 — 계층을 좁힌다

고장은 어느 한 계층에 있다. 순서대로 잘라 나간다.

```
   ① 센서    프레임이 오는가,   그 프레임에 정보가 있는가
   ② 특징    보는 자리가 맞는가, 뽑은 값이 장면과 맞는가
   ③ 판단    같은 입력에 같은 출력인가, 출력이 흔들리는가
   ④ 구동    명령한 것과 나간 것이 같은가
   ⑤ 모델    요청이 가는가, 답이 오는가, 그 답이 쓰이는가
```

각 계층에서 던질 질문:

| 계층 | 질문 | 재는 법 |
|---|---|---|
| 센서 | 프레임에 정보가 있나 | `assert_frame_sane` · 표준편차 |
| 센서 | 카메라가 내 측정을 되돌리나 | 소등/점등 **차분** · 노출 고정 |
| 특징 | 보는 자리가 맞나 | ROI 를 프레임 위에 그려 본다 |
| 판단 | 정지 장면에서 조용한가 | 20 프레임 중 전송 횟수 |
| 구동 | 명령 = 발광인가 | 명령한 색과 **촬영한 색** 대조 |
| 모델 | 전부 실패인가 일부인가 | `policy.stats` 의 requests 대 failed |

마지막 줄이 핵심이다. **전부 실패하면 전송 계층, 일부만 실패하면 계약이다.**

## 쓸 수 있는 도구

```bash
./host/sim_demo.py --fault <name> --still --steps 20   # 정지 장면 전송 빈도
./host/sim_demo.py --fault <name> --save frames/       # 프레임을 눈으로 본다
./host/sim_demo.py --fault <name> --policy vlm         # 모델 계층을 켠다
```

```python
from sim import build_rig
rig = build_rig("random-seed-17-의-결함")   # 또는 데모와 같은 시드로
with rig.source as src:
    obs = src.read()
    print(obs.image.std())                  # 센서
    print(rig.extractor(obs.image))         # 특징
    print(rig.world.emitted())              # 구동
```

## 진단 보고서 (제출물)

| 항목 | 적을 것 |
|---|---|
| 증상 | 내가 관측한 것. 들은 것이 아니라 **본 것** |
| 배제한 계층 | 어느 계층이 아니라고 판단했는가, **무슨 측정으로** |
| 지목한 계층 | |
| 원인 | |
| 근거 | 이 측정이 다른 설명을 배제하는 이유 |
| 고치는 법 | |
| 재발 방지 | 같은 고장을 **자동으로** 잡으려면 무엇을 추가해야 하나 |

마지막 줄을 비워 두면 보고서는 반쪽이다. 원인을 찾는 것보다 **다음에 자동으로
잡히게 만드는 것**이 일의 끝이다.

## 예상 출력 — 정상 장비

```
20 스텝 · 평균 17ms (촬영 13 + 특징 4 + 판단 0 + 구동 0)
명령 전송 1회 / 20 스텝  — 시리얼이었다면 4줄
```

정지 장면에서 **명령 1회**. 이 숫자를 외워 둔다. 여러 고장이 이 숫자를 바꾼다.

## 의도된 실패 실습

1. **건전성 검사를 꺼 본다**: `flat-frame` 결함에서 `source.check_health = False`
   로 두고 돌린다. 예외가 사라지고 **아무 오류 없이 "물체 없음" 만** 계속 나온다.
   어느 쪽이 더 위험한지 조별로 말한다.
2. **정상 장비를 고장으로 오진해 본다**: 결함 없이 `--fault` 를 빼고 돌리되
   `--still` 없이 색지를 계속 바꾼다. 명령 횟수가 늘어난다. 이것은 고장인가?
3. **같은 증상, 다른 원인**: `health-ok-dead` 와 `schema-drift` 를 각각 돌려
   `policy.stats` 를 나란히 적는다. 둘을 가르는 숫자 하나를 찾는다.
4. **고친 뒤 되돌려 본다**: 원인을 찾았으면 `sim/faults.py` 에서 그 결함의
   주입을 꺼 보고, 증상이 실제로 사라지는지 확인한다. **고쳤다고 믿는 것과
   고쳐진 것은 다르다.**

## 연습 문제

1. `/health` 가 ok 를 돌려주는데도 추론이 전부 실패하고 있었다. 이 상태를
   **LED 만 보고** 알아챌 수 있는가? 알아챌 수 없다면 무엇을 추가해야 하는가?
2. 정지 장면인데 명령이 20 프레임 중 11회 나갔다. 센서 노이즈가 원인이라고
   결론 내리기 전에 배제해야 할 다른 설명 두 가지를 쓰시오.
3. 진단 보고서의 "재발 방지" 칸에 "다음부터 주의한다" 라고 쓰면 왜 틀린
   답인가? 이 저장소에서 그 칸을 제대로 채운 사례를 하나 찾아 근거로 드시오.

## 교훈

> **성공 신호는 작동의 증거가 아니다.** 장치 파일이 있는 것, `/health` 가 ok 인
> 것, 스키마를 통과한 것 — 셋 다 이 저장소에서 한 번씩 사람을 속였다.
>
> 그리고 **침묵이 예외보다 위험하다.** 건전성 검사가 하는 일은 고장을 만드는
> 것이 아니라, 이미 있던 고장을 **말하게 만드는 것**이다.
