# 교육 커리큘럼 — Physical AI 기초

## 이 문서의 위치

프로젝트의 목적은 **Physical AI 기초 기술을 구현하고, 설명하기 쉬운 사례를 만들어
시범을 보이며, 교육용 커리큘럼을 완성하는 것**이다.

그래서 이 저장소의 진짜 산출물은 동작하는 코드가 아니라 **가르칠 수 있는 자료**다.
동작하는 코드는 그 자료의 일부일 뿐이다.

## 왜 이 프로젝트가 교재로 적합한가

세 가지가 우연히 맞아떨어졌다.

**1. 실패가 전부 기록되어 있다.**
교재가 가장 흔히 실패하는 지점은 "잘 되는 경우" 만 보여주는 것이다. 학습자는
막히는 순간 아무 도움도 못 받는다. 이 저장소에는 실제로 막혔던 지점과 그때
무엇을 어떻게 재어 빠져나왔는지가 남아 있다 — 그 기록이 강의안의 뼈대가 된다.

**2. 결정마다 대안과 기각 사유가 있다 (ADR).**
"이렇게 하세요" 가 아니라 "이 선택지들이 있었고 이런 이유로 이것을 골랐다" 를
보여줄 수 있다. 판단을 가르치려면 결론만으로는 부족하다.

**3. 규모가 작고 눈에 보인다.**
LED 하나가 색을 바꾸는 것은 설명이 필요 없다. 동작 여부를 학습자가 즉시 안다.

## 반복되는 세 가지 주제

모듈을 관통하는 원칙이다. 각 모듈에서 **같은 교훈을 다른 층위로** 다시 만난다.

### 주제 A — 성공 신호가 동작을 뜻하지 않는다

| 층위 | 성공처럼 보인 것 | 실제 |
|---|---|---|
| 하드웨어 | `/dev/video0` 존재 | 전 픽셀이 4100인 평탄 프레임 |
| 드라이버 | `imx477 bound` | 센서가 IMX708이라 설정 실패 |
| 서버 | `model loaded`, `/health` ok | 비전 버퍼 할당 실패, 첫 요청에 사망 |
| 모델 | 스키마 통과 | 검증기가 5회 중 4회 거부 |
| 선언 | 파일 적재 성공 | 서보는 물리적으로 없음 |

**가르칠 것:** 무엇을 근거로 "동작한다" 고 말할 것인가. 답은 언제나
**출력을 직접 재는 것**이다 — 픽셀 값, 사진 속 색, 실제 요청.

### 주제 B — 측정하지 않은 것은 모른다

- "7B가 올라갈까?" → 재보니 **단독으로는 되고 운용 중엔 죽는다**
- "카메라가 LED를 볼까?" → 재보니 **전역 밝기로는 안 보이고 국소로는 보인다**
- "VLM이 루프에 들어갈까?" → 재보니 **70~85배 느리다**
- "빨간 LED가 왜 노랑이 안 될까?" → 재보니 **공통 저항 전류 경쟁**

**가르칠 것:** 추측과 측정을 구분하는 습관. 그리고 **무엇을 재야 답이 나오는지**
설계하는 능력.

### 주제 C — 느린 것과 빠른 것을 분리하라

Physical AI 의 핵심 긴장이다. AI 판단은 초 단위, 물리 제어는 밀리초 단위다.
이 프로젝트는 이 분리를 세 번 만난다 — 점멸 타이밍(ADR-0001), VLM 비동기
(ADR-0008), 출력 이력(ADR-0007). 같은 원리의 세 얼굴이다.

## 모듈 구성

각 모듈은 **하나의 수직 슬라이스**에 대응한다. 슬라이스가 그 자체로 데모 가능하게
설계된 덕분에, 모듈마다 학습자가 눈으로 확인할 결과물이 있다.

### 모듈 0 — 환경과 하드웨어 확인
**슬라이스** Project 0  **실습서** [`labs/01-hardware-truth.md`](labs/01-hardware-truth.md)  **자료** `project_0_camtest.md`

- 실습: 카메라를 연결하고, 인식되지 않는 이유를 스스로 찾아낸다
- 핵심 경험: `/dev/video0` 이 생겼는데 사진이 평탄하다
- 도구: `journalctl -k`, `i2cdetect`, 레지스터 직접 읽기
- **교훈 (주제 A)**: 장치 노드는 드라이버가 만든다. 센서가 만드는 게 아니다.
- 흔한 막힘: 오버레이 미설정 / 미지원 센서 / 케이블

### 모듈 1 — 액추에이터와 타이밍 소유권
**슬라이스** VS-0  **실습서** [`labs/02-actuator-timing.md`](labs/02-actuator-timing.md)  **자료** `arduino/rgb_led/`, ADR-0001

- 실습: LED 점멸을 (a) 호스트 주도 (b) MCU 주도 로 각각 구현해 비교
- 핵심 경험: 100ms 주기에서 호스트 주도가 눈에 띄게 떨린다
- **교훈 (주제 C)**: 타이밍은 MCU 가 소유하고 호스트는 의도만 보낸다
- 심화: 안전 한계를 펌웨어에 두는 이유 (ADR-0003)

### 모듈 2 — 인지 계층과 테스트 가능성
**슬라이스** VS-1  **실습서** [`labs/03-perception.md`](labs/03-perception.md)  **자료** `perception/`, ADR-0004·0005·0006

- 실습: 합성 프레임 소스를 만들어 카메라 없이 상위 계층을 개발
- 핵심 경험: 평탄 프레임 검사가 실제로 불량을 잡는다
- **교훈 (주제 A)**: 픽셀로 검증한다
- 설계 교훈: 추상화가 **임계 경로를 끊는다** — 부품을 기다리며 개발할 수 있다

### 모듈 3 — 규칙 기반 폐루프와 기준선
**슬라이스** VS-2  **실습서** [`labs/04-rule-loop.md`](labs/04-rule-loop.md)  **자료** `control/`, ADR-0007

- 실습: 색 판별 → LED 반응. AI 없이 종단 연결
- 핵심 경험: 자동노출이 전역 밝기를 상쇄해 LED 가 "안 보인다"
- 핵심 경험: 노이즈만으로 20스텝 중 18회 명령이 나간다
- **교훈 (주제 B)**: 지연을 재두면 다음 단계의 비용을 알 수 있다
- **교훈 (주제 C)**: 판단 분해능을 관측 신뢰도에 맞춘다

### 모듈 4 — 온디바이스 AI 판단
**슬라이스** VS-3  **실습서** [`labs/05-ondevice-ai.md`](labs/05-ondevice-ai.md)  **자료** `control/vlm.py`, ADR-0008·0009

- 실습: 로컬 VLM 을 올리고 메모리 예산을 실측
- 핵심 경험: 7B 는 적재되지만 운용 중 죽는다 / 3B 는 더 빠르고 정확하다
- 핵심 경험: 스키마와 검증기가 어긋나 80%가 조용히 거부된다
- **교훈 (주제 C)**: 비동기 분리 — 느린 판단이 빠른 제어를 막지 않는다
- **교훈**: 모델에게 "모르겠다" 는 출구를 줘야 지어내지 않는다

### 모듈 5 — 역량 계약
**슬라이스** VS-4  **실습서** [`labs/06-capability-contract.md`](labs/06-capability-contract.md)  **자료** `capabilities/`, ADR-0010

- 실습: **코드를 한 줄도 쓰지 않고** 새 장치를 추가
- 핵심 경험: JSON 파일 하나로 모델이 보는 스키마가 늘어난다
- **교훈**: 계약을 한 곳에만 적으면 갈라질 수 없다
- 심화: 왜 모델에게 원시 명령 문자열을 만들게 하면 안 되는가

### 모듈 6 — 확장·안전·평가
**슬라이스** VS-5, VS-6  *(미완)*

- 실습: 서보·스테퍼 추가, 센서 입력, 안전 인터록, 워치독
- **교훈**: 모터를 붙이기 **전에** 안전장치를 만든다

## 교재로 완성하기 위해 남은 일

현재 저장소는 **기록은 충분하지만 교재 형태가 아니다.** 필요한 것:

| 항목 | 상태 | 비고 |
|---|---|---|
| 기술 기록·ADR | ✅ 충분 | 강의안의 원재료 |
| 재현 가능한 코드 | ✅ 동작 | 테스트 103개 |
| **단계별 실습 지침** | ✅ 모듈 0~5 | 모듈 6 은 부품 도착 후 |
| **예상 출력** | ✅ 모듈 0~5 | 전부 실제 관측값 |
| **의도된 실패 실습** | ✅ 모듈 0~5 | 모듈당 2~4개, 모두 실제 사건 |
| **연습 문제** | ✅ 모듈 0~5 | 모듈당 3문항 |
| 강사용 해설·정답 | ✅ `labs/INSTRUCTOR.md` | 해답 18문항 + 막힐 지점 |
| 영상 시연 | ❌ 없음 | 다음 단계 |
| 실제 수업 검증 | ❌ 없음 | 한 번 가르쳐 보고 보완 |
| **부품 목록·배선도** | ✅ `labs/00-setup.md` | 실제로 막혔던 부품 함정 포함 |
| 영상/사진 자료 | 일부 | 색 검증 사진은 있음 |

### 의도된 실패 실습 (이 교재의 차별점)

각 모듈에 **일부러 고장 내보는 실습**을 넣는다. 증상을 먼저 겪어야 진단을 배운다.

- 모듈 0: 오버레이를 틀리게 지정하고 `-121` 을 관찰
- 모듈 1: 호스트 주도 점멸로 지터를 눈으로 확인
- 모듈 2: `check_health=False` 로 평탄 프레임을 통과시켜 보기
- 모듈 3: 이력을 끄고 LED 떨림을 관찰
- 모듈 4: 스키마에서 `colour` 를 선택으로 되돌려 80% 거부를 재현
- 모듈 5: 선언 범위를 펌웨어보다 넓게 적고 무엇이 막는지 확인

이 실습들은 **모두 실제로 일어났던 일**이므로 지어낼 필요가 없다.

## 권장 진행 순서 변경

원래 계획은 VS-5 → VS-6 으로 기능을 넓히는 것이었다. 교육 목적을 고려하면
**모듈 0~5 를 교재로 완성하는 것이 먼저**다. 이유:

- 지금 있는 것만으로도 **완결된 한 사이클**(인지 → 판단 → 구동)이 성립한다
- 기억이 선명할 때 실습 지침을 적어야 정확하다
- 모듈 6 은 서보 등 **부품이 실제로 도착한 뒤**에 쓰는 것이 맞다

`servo_pointer` 를 `status: planned` 로 선언해 둔 것이 이 순서와 맞는다 —
계약 구조는 가르칠 수 있고, 실물 실습은 부품이 오면 추가한다.
