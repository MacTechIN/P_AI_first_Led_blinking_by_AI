# ADR-0010 — 액추에이터는 코드가 아니라 데이터로 선언한다

상태: 채택   날짜: 2026-09-18   슬라이스: VS-4

## 배경
정의서는 "프로그램 불필요" 와 "액추에이터 구성은 사용자가 입력" 을 요구한다.
VS-2·VS-3 의 경로는 `LedCommand` 라는 **LED 전용 자료형**과 시리얼 문법을 아는
파이썬 액추에이터로 되어 있었다. 서보를 붙이려면 자료형·정책·액추에이터를 모두
고쳐야 했고, 그 순간 요구가 깨진다.

## 결정
장치를 `capabilities/*.json` 에 선언한다. 한 선언에서 **세 가지가 파생된다**:

1. 모델에게 주는 JSON 스키마 (`Registry.tool_schema`)
2. 출력 검증기 (`Registry.validate`)
3. 전송 문자열 (`CommandSpec.wire` 템플릿)

`ContractActuator` 는 **전송 방식마다** 하나씩만 있고 장치마다 있지 않다.

## 근거
`wire` 템플릿이 핵심이다. 이것이 없으면 장치마다 파이썬 어댑터가 필요하고,
"선언만 추가" 가 성립하지 않는다.

스키마와 검증기를 한 선언에서 뽑는 것은 ADR-0009 의 교훈이 강제한 것이다.
VS-3 에서 계약을 두 곳에 적었더니 갈라졌고 응답의 80%가 거부됐다. 여기서는
계약이 한 곳에만 있으므로 갈라질 수 없다.

## 대안과 기각 사유
- **장치마다 파이썬 클래스**: 관례적이지만 "프로그램 불필요" 를 정면으로 어긴다. 기각.
- **`LedCommand` 를 일반화**: 자료형 하나로 모든 장치를 표현하려면 결국
  선언적 스키마가 된다. 이름만 다른 같은 것이다.
- **모델에게 원시 시리얼 문자열 생성 허용**: 범위 검사가 불가능하고 환각이
  그대로 하드웨어에 닿는다. 기각.

## 결과
- **합격 판정 (µ4.4)**: `test_adding_a_device_needs_no_code`.
  실제로도 확인했다 — `servo_pointer.json` 을 추가하자 파이썬 md5 가 그대로인 채
  모델이 보는 스키마가 3옵션/1장치에서 5옵션/2장치로 늘었다.
- 범위는 여전히 **펌웨어에도** 중복 구현한다 (ADR-0003). 호스트 검증은 우회될 수
  있고, 선언은 데이터이므로 잘못 적힐 수도 있다.
- VS-2·VS-3 의 `LedCommand` 경로는 그대로 둔다. 규칙 정책의 기준선 가치가 남아
  있고, 두 경로가 같은 펌웨어 위에서 동작한다.
- 계약 스키마가 복잡해지면서 VLM 지연이 늘었다 (1.3초 → 4.1초). `oneOf` 분기가
  많아진 탓으로 보인다. VS-6 에서 장치가 더 늘면 재검토해야 한다.

## 실물보다 선언이 먼저 존재하는 경우

`servo_pointer` 는 **아직 물리적으로 장착되지 않았다.** 계약 구조를 검증하려고
선언만 먼저 만든 것이다. 이런 상태를 선언 안에 적는다:

```json
"status": "planned",
"transport": {"type": "null"}
```

`status: planned` 인데 전송로가 `null` 이 아니면 **적재 시점에 거부**한다.
실물 없는 장치가 살아 있는 포트로 명령을 보내는 사고를 구조적으로 막는다.
모델이 보는 목록에도 `[not wired yet]` 로 표시된다.

이는 이 프로젝트가 반복해서 배운 것과 같은 원칙이다 — **선언·적재·표시가 성공해도
실제로 동작한다는 뜻이 아니다.** `/dev/video0` 이 있다고 카메라가 찍히는 게
아니었고(ADR-0005), `model loaded` 가 서빙 가능을 뜻하지 않았다. 여기서도 마찬가지다.
