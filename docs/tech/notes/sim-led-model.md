# 가상 LED 발광 모델 — 어디까지 맞고 어디부터 틀리는가 (2026-10-19)

S-1 의 `sim/panel.py` 가 명령을 빛으로 바꾸는 방식, 그 계수를 어떤 실측에서
풀었는지, 그리고 **실물과 어긋나는 구간**을 남긴다.

전제: `docs/tech/notes/rgb-led-calibration.md` 의 두 하드웨어 문제.

## 두 단계

```
LedCommand ──[펌웨어]──> 듀티 ──[하드웨어]──> 발광 ──> 카메라
             dutyFor()         공통 저항 경쟁
```

펌웨어 단계는 흉내가 아니라 **같은 식**이다. `값 × level/255 × gain/255`,
각 단계마다 정수 버림. 부동소수로 바꾸면 값이 달라지므로 시험으로 고정했다.

하드웨어 단계가 이 문서의 주제다.

## 경쟁 모델

순방향 전압이 낮은 다이가 이긴다. 발광량을

```
raw_i  = (duty_i / 255) ** EXPONENT × STRENGTH_i
share  = raw / sum(raw)
발광_i = share_i × (max(duty)/255) × 255
```

로 둔다. 저항이 하나이므로 총 전류가 묶이고, 셋이 그것을 나눠 갖는다는 뜻이다.

## 계수를 어디서 풀었나

교정 기록의 검증 실험 **세 점**이 전부다. 모두 B=0, 초록 듀티 255 고정:

| 듀티 (R, G) | 기록된 색조 | 모델 | 차이 |
|---|---|---|---|
| (255, 255) | 0 | 3 | +3 |
| (120, 255) | 38 | 40 | +2 |
| (60, 255) | 58 | 58 | 0 |

색조에서 발광비를 되돌리면 `r/g = 9.21 × (d_r/d_g)^3.46` 이 세 점을 모두 지난다.
그래서 `EXPONENT = 3.46`, 적:녹 강도비 = 1 : 0.109 이다.

**청색 강도는 실측이 아니다.** 기록에 남은 것은 순서(적>녹>청)와 "청록이
초록으로 나왔다" 는 사실뿐이라, 적:녹과 같은 비율을 한 칸 더 적용한 외삽이다.

## 어긋나는 구간 — 혼합색에서 시뮬레이터가 더 나쁘다

이득 보정(`GAIN_R=120, GAIN_G=200, GAIN_B=255`)을 적용한 **현재 배선**에서
여섯 색을 돌린 결과:

| 명령 | 시뮬레이터 발광 | 색조 | 판정 |
|---|---|---|---|
| red | (120, 0, 0) | 0 | red ✔ |
| green | (0, 200, 0) | 60 | green ✔ |
| blue | (0, 0, 255) | 120 | blue ✔ |
| yellow | (122, 78, 0) | 19 | **orange ✘** |
| cyan | (0, 204, 51) | 67 | **green ✘** |
| magenta | (220, 0, 35) | 175 | **red ✘** |

**시뮬레이터 3/6. 같은 조건의 실물은 6/6 이었다** (평균 색조 오차 7.7).

원색 셋은 맞고 혼합 셋이 전부 강한 다이 쪽으로 밀렸다. 원인은 분명하다 —
계수를 푼 세 점이 **초록 듀티 255 한 줄 위에만** 있다. 이득 보정은 운용점을
그 줄 밖으로 옮기는데, 거기서 모델은 외삽이고 경쟁을 과대평가한다.

산술로 보면: 듀티 (120,255)→(120,200) 으로 초록을 0.784 배 할 때 실물이
노랑으로 읽히려면 발광비가 0.73 배만 줄어야 한다(지수 1.29). 같은 줄의 세 점은
지수 3.46 을 요구한다. **한 줄의 데이터로 두 방향을 결정할 수 없다.**

### 그래서 어떻게 하나

고치지 않고 남긴다. 이유는 둘이다.

1. **없는 데이터를 지어내면 그게 더 나쁜 버그다.** 지수를 1.29 로 낮추면 실측
   세 점이 깨지고, 두 값을 섞어 쓰면 아무 근거 없는 곡선이 된다.
2. **이 어긋남 자체가 실습 재료다.** "시뮬레이터는 주황이라 하고 실물은
   노랑이라 한다. 어느 쪽이 틀렸고 어떻게 알아내나" 는 이 교재가 가르치는
   방법 그대로다. 답은 **듀티 격자를 재서 다시 맞추는 것**이다.

### 닫는 방법

`(d_r, d_g)` 를 격자로 돌려 색조를 기록하고 2차원에서 다시 맞춘다.

```bash
./host/verify_rgb.py --level 40 --lock      # 실물에서 잰다
```

새 점은 `tests/test_sim.py` 의 `MEASURED` 에 추가한다. 계수를 건드리면
거기서 먼저 깨지므로, 되돌아갈 수 없게 된다.

## 코어 포화

실물에서 **LED 코어는 어떤 색이든 카메라를 포화시켜 흰색이 된다.** 색은
주변부에만 남는다. 렌더링이 이것을 재현한다(`BLOOM_KNEE`). 재현하지 않으면
"포화 화소를 빼야 한다" 는 측정 교훈을 실습에서 보여줄 방법이 없다.

## 켜고 끌 수 있는 것

| 스위치 | 기본 | 끄면 |
|---|---|---|
| `shared_resistor` | True | 채널마다 저항이 있는 **올바른 배선**. 노랑이 노랑으로 나온다 |
| `polarity_fixed` | True | 공통 애노드 반전 미적용. 빨강이 청록, 흰색이 소등 |
| `gains` | 펌웨어 값 | `(255,255,255)` 로 두면 보정 전 상태 |

세 스위치 모두 **기본값이 현재 실물**이다. 잘 되는 상태를 기본으로 두면
시뮬레이터가 해피패스를 가르치게 된다.
